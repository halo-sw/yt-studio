# 기획서 05 — 함께 결정 (2/3 투표)

## 1. 개요

3인 공동 운영에서 한 사람이 단독으로 정하면 안 되는 사안(제목 시안, 썸네일,
바이블 변경, 신규 화면 추가 같은 스코프 변경)을 2/3 다수결로 처리하는 화면.
주 사용자: 3인 전원.

## 2. 목표·성공 기준

- 결정 대기 항목이 24시간 이상 방치되지 않게, 홈 피드와 연동해 투표를 독촉.
- 데모 합격 기준: 안건에 두 번째 표가 들어오는 순간 상태가 `가결`로 바뀌고
  결과가 기록에 남는다.

## 3. 사용자 시나리오

- B가 일본 머니 제목 3안 중 선택 안건 등록 → A·C에게 홈 피드 알림 → A 1안,
  C 1안 → 2/3 충족 즉시 가결 → publish.py가 1안으로 예약 진행.
- 드라마썰 바이블 금지어 추가 제안 → 2표 미달로 48시간 경과 → `유찰` 처리.

## 4. 화면 구성

- 상단 탭: `진행 중` / `끝난 결정`.
- 안건 카드: 제목, 발의자, 마감까지 남은 시간, 선택지(제목 3안이면 3버튼 +
  각 안 미리보기), 현재 득표(누가 어디 찍었는지 공개 — 3인 팀이라 익명 무의미),
  내 투표 버튼.
- 안건 등록 폼: 유형(제목/썸네일/바이블 변경/기타), 선택지 2~4개, 마감(기본 48h).

## 5. 핵심 인터랙션

- **투표하기**: 선택지 클릭 즉시 반영, 마감 전 변경 가능.
- 같은 선택지 2표 도달 → 자동 `가결` + 후속 액션 연결(제목이면 에피소드 메타에
  기록, 바이블 변경이면 yaml 수정 PR 안내).
- 발의자도 투표 가능(3인 중 1표) — 단 발의자 1표만으로는 아무것도 확정되지 않음.

## 6. 데이터·API 매핑

- `VoteModel(topic, card_id, voter, choice)` — 안건은 topic 단위 그룹.
  (M2에서 안건 테이블 분리 여지 있음 — 현재는 최소 스키마.)
- `GET /votes`, `POST /votes/{topic}/cast`. 가결 판정은 서버(2/3 = 2표).
- 가결 결과는 `AuditLogModel`에 기록 (actor="vote:2/3").

## 7. 절대 규칙 반영 (§5·§10)

- **§10 스코프 확장 금지**: "신규 화면 추가" 유형 안건이 여기서 3인 합의를
  얻기 전에는 기획서(docs/plans)에 새 화면을 추가하지 않는다 — 이 화면이
  그 합의의 공식 통로.
- 바이블(잠금 자산) 변경도 반드시 이 화면 경유 — 가결 전 yaml 수정 금지.
- 투표·가결 전부 감사 로그 기록 (4장: 모든 전환 기록 원칙의 확장).

## 8. 엣지케이스

- 3인 3색(1:1:1) 마감 도달: `유찰` — 발의자에게 재발의 유도.
- 마감 전 선택지 수정: 이미 투표 있으면 수정 불가, 안건 취소 후 재등록만.
- 발의자가 안건 취소: 득표 있어도 가능하나 취소 이력이 기록에 남음.

## 9. 데모 체크리스트

- [ ] 진행 중 안건에 현재 득표가 실명으로 보인다
- [ ] 두 번째 표 입력 순간 `가결` 배지로 바뀐다
- [ ] 끝난 결정 탭에 결과와 시각이 남는다
- [ ] 바이블 변경 유형 안건이 등록 폼에 존재한다
